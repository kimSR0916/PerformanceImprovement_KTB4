카카오 약관 결과기 — RAG 파이프라인 해설

kakao_terms_rag_cell1.py 한 파일이 어떻게 "카카오계정을 탈퇴하려면 어떻게 하나요?" 같은 질문을 받아, 수백 개 조항 중 진짜 관련 있는 몇 개만 찾아내고, 그것만 근거로 Qwen2.5-7B가 답을 쓰게 만드는지 처음부터 끝까지 따라가 봅니다.

1. 배경

RAG란 무엇인가 — 초심자를 위한 깊은 배경

이미 RAG, 임베딩, 벡터 검색에 익숙하다면 이 단락은 건너뛰고 이 과제의 계약 조건으로 바로 가도 좋습니다.

거대 언어모델(LLM)에게 "카카오계정을 탈퇴하는 방법은?"이라고 물으면, 모델은 학습 당시 봤던 데이터를 바탕으로 그럴듯한 답을 지어낼 수 있습니다. 문제는 실제 약관 조항의 정확한 문구나 최신 개정 내용은 모델이 몰랐거나 틀리게 기억하고 있을 수 있다는 점입니다. 이걸 흔히 "환각(hallucination)"이라 부릅니다.

가장 단순한 해결책은 "약관 전체를 프롬프트에 다 넣고 그 안에서 찾아서 답해"라고 시키는 것입니다. 실제로 작은 문서라면 이 방법도 통합니다. 하지만 카카오의 약관 네 종류를 합치면 수백 개의 조항, 수만 자에 달하고, 질문마다 이걸 전부 모델에 입력하면 (1) 매번 계산량이 커져 느려지고, (2) 모델이 정작 중요한 조항을 수많은 무관한 텍스트 속에서 놓치기 쉬워지고, (3) 이번 과제에서는 애초에 금지된 방식이기도 합니다.

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 이 문제를 "먼저 찾고, 찾은 것만 갖고 답하게 하자"는 방식으로 풉니다. 질문이 들어오면:

  1. 전체 문서를 작은 조각(청크)으로 미리 나눠 둔다 — 여기서는 "조(條)" 단위.
  2. 질문과 각 조각의 관련도를 계산해 상위 몇 개만 골라낸다 (검색, retrieval).
  3. 고른 조각만 프롬프트에 넣고 LLM에게 "이 안에서만 답을 찾아라"라고 지시한다 (생성, generation).

관련도를 계산하는 대표적인 두 가지 방법이 있습니다.

밀집 검색 (Dense / 임베딩)

문장을 숫자 벡터로 바꾸는 "임베딩 모델"을 씁니다. 의미가 비슷한 문장은 벡터 공간에서 가까이 놓입니다. "탈퇴"와 "해지"처럼 단어는 달라도 뜻이 비슷하면 잡아낼 수 있습니다.

희소 검색 (Sparse / 키워드, BM25)

전통적인 키워드 매칭 방식입니다. 질문에 등장한 단어가 문서에도 등장하는지, 얼마나 자주·희귀하게 등장하는지를 점수화합니다. 법률 문서의 고유명사·조항 번호처럼 "정확히 그 단어"가 중요할 때 강합니다.

이 결과기는 두 방식을 하이브리드로 섞어 씁니다. 자세한 계산은 아래 코드 해설에서 다룹니다.

마지막 조각은 LLM 자체를 GPU에 어떻게 올리느냐입니다. Colab의 무료 T4 GPU는 메모리가 16GB뿐이라, 70억(7B) 개 파라미터를 가진 Qwen2.5-7B-Instruct를 원래 정밀도(16비트)로 올리면 약 14GB를 혼자 다 써버려 임베딩 모델이나 검색 인덱스가 들어갈 자리가 없습니다. 4비트 양자화는 각 파라미터를 저장하는 비트 수를 16비트에서 4비트로 줄여, 모델 크기를 대략 4분의 1(약 4~5GB)로 압축합니다. 정확도는 약간 손해 보지만 T4 한 장에 전체 파이프라인을 올릴 수 있게 해줍니다.

최종적으로 상위 조항(여기선 제9조 하나, 실제로는 최대 4개)만 아래처럼 프롬프트에 들어갑니다.

3. 코드 해설

전체 흐름을 여섯 덩어리로 나눠 순서대로 봅니다. 패키지 설치 부분은 생략하고(단순 pip install) 로직이 있는 부분부터 시작합니다.

① 원문 수집·파싱

먼저 문서 이름마다 후보 URL 목록을 둡니다. 첫 URL이 실패하면 다음 걸 시도하는 폴백 구조입니다. "카카오 통합 약관"처럼 전용 페이지가 불확실한 경우, 통합서비스약관 페이지를 예비 소스로 재사용하도록 해뒀습니다. 

TERMS_SOURCES = {
    "카카오계정 약관": [
        "https://www.kakao.com/policy/terms?type=a&lang=ko",
    ],
    "카카오 통합 약관": [
        "https://www.kakao.com/policy/terms?type=t&lang=ko",
        "https://www.kakao.com/policy/terms?type=ts&lang=ko",  # 폴백
    ],
    ...
}

페이지를 받아오면 BeautifulSoup으로 스크립트·헤더·푸터 등 본문과 무관한 태그를 걷어내고, 순수 텍스트만 줄 단위로 남깁니다. 그 다음 정규식으로 "조" 경계를 찾습니다. 

_ARTICLE_PATTERN = re.compile(r"^제\s*(\d+)\s*조\s*(?:\(([^)]{0,80})\))?", re.MULTILINE)
핵심은 맨 앞의 ^과 re.MULTILINE 조합입니다.

약관 본문에는 "제9조에 따라 회사는..."처럼 다른 조문 안에서 조항 번호를 인용하는 문장이 흔합니다. 만약 ^ 없이 그냥 제\d+조로 찾으면 이런 인용문까지 전부 "새 조의 시작"으로 오인해 본문이 잘게 찢어집니다. 실제 조 제목은 항상 줄 맨 앞에서 시작한다는 점(제 9 조 (이용계약 해지))을 이용해, "줄의 시작 지점에서만" 매칭하도록 anchor를 건 것입니다.

찾은 경계들 사이의 텍스트를 각각 하나의 조 청크로 자르고, 너무 긴 조는 _subsplit_long_article로 문단 단위 서브 청크로 다시 나눕니다 (조 번호는 그대로 유지되어, 나중에 검색 결과에서 원래 어느 조에 속했는지 알 수 있습니다).

② 밀집 검색 — KURE 임베딩 + FAISS

_EMBED_MODEL = SentenceTransformer("nlpai-lab/KURE-v1", device=...)

_CORPUS_EMB = _EMBED_MODEL.encode(
    _CORPUS_TEXTS, normalize_embeddings=True, ...
).astype("float32")

_FAISS_INDEX = faiss.IndexFlatIP(_CORPUS_EMB.shape[1])
_FAISS_INDEX.add(_CORPUS_EMB)

KURE-v1은 고려대에서 만든 한국어 검색 특화 임베딩 모델로, 문장을 1024차원 벡터로 바꿔줍니다. 여기서 눈여겨볼 디테일은 normalize_embeddings=True와 IndexFlatIP의 조합입니다. 벡터를 단위 길이(크기 1)로 정규화해두면, 두 벡터의 내적(inner product)이 곧 코사인 유사도와 같아집니다. 그래서 "거리"가 아니라 "내적이 큰 순"으로 찾는 IndexFlatIP를 쓰면 바로 의미적으로 가장 가까운 조항을 찾는 것과 같아집니다.

③ 희소 검색 — BM25

_TOKEN_PATTERN = re.compile(r"[가-힣]+|[a-zA-Z0-9]+")

def _tokenize(text: str):
    return _TOKEN_PATTERN.findall(text.lower())

_BM25 = BM25Okapi([_tokenize(t) for t in _CORPUS_TEXTS])

형태소 분석기(예: KoNLPy) 없이, 한글 연속 구간과 영숫자 연속 구간을 단순히 토큰으로 뽑는 가벼운 정규식 토크나이저를 씁니다. 완벽한 형태소 분리는 아니지만, 별도 자바 의존성 없이 Colab에서 바로 돌아가고, BM25가 필요로 하는 "이 단어가 이 문서에 있는가" 판단에는 충분합니다.

④ 하이브리드 재순위화

_hybrid_search가 실제 질의 시점 로직입니다. 밀집 검색 상위 20개와 희소 검색 상위 20개의 합집합을 후보로 모은 뒤, 두 점수를 각각 min-max 정규화(0~1 범위로)하고 가중합을 계산합니다. 

combined = dense_weight * dense_vals + (1 - dense_weight) * bm25_vals  # dense_weight=0.65

results, seen = [], set()
for idx, score in ranked:
    item = _RAW_CORPUS[idx]
    key = (item["doc"], item["article_no"])
    if key in seen:
        continue
    seen.add(key)
    results.append({**item, "score": float(score)})
    if len(results) >= top_k:
        break

마지막 루프의 seen 집합이 하는 일이 중요합니다. 긴 조는 여러 서브 청크로 나뉘어 있으므로(②의 _subsplit_long_article), 같은 조에서 나온 두 서브 청크가 둘 다 상위권에 오를 수 있습니다. 이때 (문서명, 조번호)가 같으면 하나로 취급해 중복 없이 최대 4개의 서로 다른 조를 반환하도록 걸러냅니다 — 계약이 요구하는 "1~4개의 핵심 근거"를 지키는 지점입니다.

    torch_dtype=torch.float16,
)

nf4(NormalFloat4)는 신경망 가중치의 실제 분포(정규분포에 가까움)에 맞춰 설계된 4비트 양자화 방식으로, 단순 균등 4비트보다 정보 손실이 적습니다. bnb_4bit_use_double_quant는 양자화에 쓰이는 스케일 값 자체도 한 번 더 압축해 메모리를 추가로 아낍니다. compute_dtype=torch.float16은 실제 행렬 곱 연산은 16비트로 수행한다는 뜻인데, T4는 Ampere 이전 세대(Compute Capability 7.5)라 bfloat16을 지원하지 않기 때문에 float16을 택했습니다.

답변 생성부는 검색된 근거를 시스템 프롬프트의 규칙과 함께 채팅 템플릿에 넣고, do_sample=False(그리디 디코딩)으로 답을 생성합니다. 약관 QA처럼 "정답이 근거 문서 안에 있는" 과제에서는 창의성보다 일관성이 중요하므로 샘플링을 끄는 것이 합리적인 선택입니다.

⑥ answer_question — 모든 것을 잇는 진입점

def answer_question(question: str):
    if not isinstance(question, str) or not question.strip():
        raise ValueError("question은 비어 있지 않은 문자열이어야 합니다.")

    question = question.strip()
    contexts = _hybrid_search(question, top_k=4)

    if not contexts:
        return {"answer": "약관에서 관련 근거를 찾을 수 없습니다.", "retrieved": []}

    prompt = _build_prompt(question, contexts)
    answer_text = _generate(prompt)
    retrieved = [[c["doc"], c["article_no"]] for c in contexts]
    return {"answer": answer_text, "retrieved": retrieved}

이 함수 자체는 짧습니다 — 앞서 만든 하이브리드 검색과 생성 함수를 순서대로 부를 뿐입니다. 흥미로운 점은 검색 결과가 하나도 없을 때(contexts가 빈 리스트)를 별도로 처리한다는 것입니다. 이 경우 굳이 LLM을 호출하지 않고 바로 "근거를 찾을 수 없습니다"를 반환해, 근거 없는 상태에서 모델이 답을 지어내는(환각) 상황 자체를 원천 차단합니다.

마지막으로 고정된 FastAPI 연결부(2번 셀이 호출하는 부분)는 threading.Lock()으로 /answer 요청을 감쌉니다. GPU 위에 올라간 생성 모델은 한 번에 하나의 요청만 안전하게 처리할 수 있는데, FastAPI가 동시에 여러 요청을 받을 경우 이 락이 두 번째 요청을 첫 번째가 끝날 때까지 대기시켜 GPU 연산이 뒤섞이는 것을 막습니다.
